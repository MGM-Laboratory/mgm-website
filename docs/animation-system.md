# Animation System (GSAP)

All site animation is **GSAP 3.15.0** (+ ScrollTrigger, ScrollSmoother). "Heavy animations everywhere" is an explicit design goal — but every animation must degrade gracefully under `prefers-reduced-motion`.

## Setup & conventions

- Plugins registered in `scroll-reveal.ts` (ScrollTrigger) and `smooth-scroll.tsx` (ScrollSmoother).
- **Scroll reveal**: `fadeUpOnScroll(root, selector, {start: "top 85%", stagger, y: 24})` — one timeline with a **timeline-level** ScrollTrigger, `once: true`. Under reduced motion it synchronously `gsap.set(targets, {opacity: 1, y: 0})` and returns null (no animation, therefore no race with hover timelines).
- **Smooth scrolling**: `<SmoothScroll>` in the root layout wraps everything; NOT created under reduced motion.
- **Reduced motion**: components check `matchMedia("(prefers-reduced-motion: no-preference)")`. The pattern is `const d = reduced ? 0 : 1;` and multiplying durations by `d` — timelines still run (content must stay reachable) but collapse to instant swaps. Decorative loops (idle breathing, social wiggle) are skipped entirely under reduced motion.
- **Hydration-safe clock** (`"--:--"` server-side, real time in effect) is the pattern for any time-dependent UI.
- **React 19**: refs pass as props (`ref={ref}`) on function components — no `forwardRef`.

## Gotchas (each of these has already cost real debugging time)

### 1. Never let a CSS class set transform on an element GSAP animates

GSAP **stacks onto** a pre-existing CSS-class transform instead of replacing it (observed twice: `translate-y-full` made a `yPercent` tween a no-op; a static `[transform:translateX(100%)]` class compounded with GSAP's `xPercent` to a 200% offset — computed style was literally `translate(100%,0%) translate(460px,0px)`). Tailwind v4's `translate-x-full` sets the separate CSS `translate` property — same failure mode.

**Rule:** GSAP must be the _only_ thing touching `transform`/`translate`/`rotate`/`scale` on an element, from first paint on (explicit `gsap.set()` in a mount effect). For pre-hydration "hidden" defaults use **opacity/visibility only** (`invisible opacity-0` — GSAP's `autoAlpha` cleanly overrides them).

### 2. `.fromTo()` renders its "from" state at creation (`immediateRender: true` default)

Even inside a `paused: true` timeline, creating a `.fromTo()` immediately applies the "from" values. Under reduced motion all durations collapse to 0, so "from" and "to" are the same instant — every card snapped to its hovered state **on mount, before any hover**. Fix: `immediateRender: !reduced` on such tweens. (`immediateRender` cannot be part of `defaults` — it's per-tween. Also note: `defaults: {immediateRender: false}` does not work reliably across GSAP versions; set it explicitly per tween.)

### 3. Hover-vs-entrance races: use `.fromTo()` baselines, not `.to()`

When a hover timeline and a scroll entrance (or idle loop) animate the **same property of the same element**, a plain `.to()` adopts "current value" as its implicit start. Hovering mid-entrance lets `overwrite: "auto"` kill the entrance at a partial value, and reversing the hover timeline returns to that **stuck half-finished value forever** — the famous Core Competencies bug (cards stuck lower than the others, sometimes `opacity: 0`).

**Fix pattern** (see `core-competencies.tsx`, heavily commented): build the hover timeline with `.fromTo()` specifying the true rest baseline (`{y: 0, opacity: 1}`, `{scale: 1}`), `immediateRender: !reduced`. Reduced motion doesn't need the protection (its entrance is a synchronous `gsap.set`, already resolved before any hover).

### 4. ScrollTrigger: use timeline-level triggers, not tween-level

GSAP 3.15.0 throws inside ScrollTrigger's internal refresh when a **tween-level** `scrollTrigger` is created after ≥4 other ScrollTriggers exist on a page that loaded already scrolled down (e.g. reload mid-page). `fadeUpOnScroll` deliberately builds a timeline with a timeline-level trigger (`gsap.timeline({ scrollTrigger: {...} })`). Don't regress to `gsap.fromTo(el, {...}, { scrollTrigger })` on this codebase.

### 5. SSR flash prevention (server HTML has no JS)

Anything hidden only by a mount-effect `gsap.set()` flashes visible on first paint / reload. Give closed-state defaults via static classes (opacity/visibility only — gotcha #1), and let the mount effect position the rest. Verified with a `javaScriptEnabled: false` Playwright context: server HTML must show nothing of the closed panel.

### 6. Panels inside collapsed clips

A panel mounted inside a `height: 0` accordion clip can't establish its starting transform value — `gsap.to(panel, {yPercent: 0})` may no-op. Set the start explicitly with `gsap.set(panel, {yPercent: 100})` on mount (see `work-bento.tsx`).

### 7. Stacking contexts & z-index under transforms

GSAP's transform creates its own stacking context, so a child with a stray `z-10` can paint over a sibling overlay that animates in later (observed: front title painting over the Our Work reveal panel — fixed by removing the z-10). Keep z-index flat inside animated subtrees.

### 8. A GSAP-owned CSS property can't also be styled by a stylesheet rule

Any tween's end state is an **inline style** (`element.style.opacity = ...`), and inline styles beat every stylesheet rule on the same property regardless of selector specificity — `!important` aside. `fadeUpOnScroll` leaves `opacity: 1` sitting in `style` on every revealed element forever, so a later stylesheet rule that also targets `opacity` on that element (e.g. a filter/dimming feature keyed off a data attribute) silently no-ops on anything that already played its entrance. **Rule:** if a feature needs to style a property from a plain stylesheet rule, make sure no GSAP tween anywhere on the page ever sets that same property inline on the same elements — pick an untouched property (`filter`, a custom property consumed by `filter`/`background`, etc.) rather than fighting inline-style specificity.

### 9. `loading="lazy"` doesn't work on content moved by a continuous transform

An element repositioned every frame by an imperative `element.style.transform` (rAF loops, not real document scroll — e.g. `about/drift-wall`'s per-column tracks) can sit genuinely off-screen at mount even though it will drift into view seconds later. Native lazy-loading only fetches an image once it's actually within the viewport-distance threshold, so tiles that start off-screen don't even begin fetching until the drift carries them in — for a slow, minutes-long loop this reads as permanently broken/blank content. Measured on the team wall: `loading="lazy"` loaded 29/228 images after 3.5s; `loading="eager"` loaded 228/228. **Rule:** any image inside a perpetually-animating, off-screen-by-design container should be `loading="eager"` — the component already only mounts once its section scrolls into view, so there's no real lazy-load benefit being given up.

### 10. A bare `ScrollTrigger.create()` is the same forbidden shape as a tween-level trigger

Gotcha #4 says to use a timeline-level `scrollTrigger`, not a tween-level one — but a **standalone** `ScrollTrigger.create({ trigger, start, onEnter, onLeaveBack })` with no tween or timeline attached at all hits the exact same GSAP 3.15.0 internal-refresh bug. Found in `sections/cta-footer.tsx`'s `BackToTop`: it called `ScrollTrigger.create()` directly, and since `CtaFooter` remounts on every client-side navigation, this fired on almost any route change once ≥4 other ScrollTriggers already existed on the destination page — an uncaught `TypeError: Cannot read properties of undefined (reading 'end')` inside GSAP's own `refresh()`, with no error boundary in this app, meaning Next's dev error overlay (or a blank prod page) and a required reload. **Fix:** wrap the exact same config in an empty timeline instead — `gsap.timeline({ scrollTrigger: {...} }).scrollTrigger` — and use that returned `ScrollTrigger` instance for cleanup (`.kill()`). `onEnter`/`onLeaveBack` behave identically either way. Confirmed with a scripted navigation fuzzer (random scroll + click across every route, watching for `pageerror`): 1 crash in 51 navigations before the fix, 0 in 136+ after.

### 11. A `once: true` ScrollTrigger doesn't fire retroactively if it mounts already past `start`

`onEnter` (and therefore the entrance timeline `fadeUpOnScroll` builds) only fires on an actual **forward crossing** of the trigger's `start` position — not on creation, even if the current scroll position is already past it. On a client-side navigation, a page's data-fetched sections (and the `RevealSection`/`fadeUpOnScroll` call wrapping them) can mount several commits after the route change — by which point the visitor may already be scrolled past where that trigger's `start` would be. No crossing event ever happens, so the timeline silently never plays, and the section — most visibly the shared footer's `.footer-reveal` content — stays at its `opacity: 0` "from" state forever. Reproduced most easily via a bounce navigation (leave the page, come back) followed by scrolling straight to the bottom before the new page's triggers exist yet.

**Fix** (see `lib/scroll-reveal.ts`): right after creating the timeline, check `tl.scrollTrigger.progress > 0` — this getter reflects the true current scroll position regardless of whether a crossing event fired — and if so, jump straight to the resolved end state (`tl.progress(1)`, plus a direct `gsap.set(targets, { opacity: 1, y: 0 })` as defensive redundancy) instead of waiting for a crossing that already happened. This resolved the bug for every page except the homepage specifically; see the "Known issues" section below for the residual ScrollSmoother-specific case.

**A fix that made this worse, for the record:** an explicit `ScrollTrigger.refresh()` scheduled at a few delays after every route change (to catch triggers created before their content had visually settled) was tried and reverted — it turned a 28-repro baseline into 36, including a full-section cascade failure (every reveal on `/about` stuck at once). Recalculating trigger positions while other triggers are still mid-setup is worse than not recalculating at all; don't reach for a blanket `refresh()` here.

## Homepage ambient interactions

- Desktop entrance: the arrow starts immediately after the blue leaves finish, draws in 0.55s, and hands off to the closing line after a 0.02s pause. Closing characters use 0.36s duration and 0.014s stagger.
- After entrance (or an internal return), the X rotates clockwise in eased 90-degree steps with 2.8s rests. The red star sways, background motifs float, and headline wrappers share the shape parallax. Wrappers keep pointer translation separate from entrance/idle transforms. Idle loops pause offscreen and in hidden tabs; reduced motion skips them.
- The hero allows vertical overflow and keeps its corner ring inside the viewport, so the ring bridges into the process section without clipping.
- The mosaic has a continuous middle row with irregular upper/lower gaps. It moves exactly one 18-tile copy width and renders enough copies for the viewport, including ultrawide screens and reduced motion.
- `InteractiveBackground`, outside the smooth-scroll transform, draws a faint theme-colored cursor wake without loading assets. Input is sampled, wake count and pixel ratio are bounded, and rendering stops once the trail fades. Touch and reduced-motion visitors get no wake; all listeners and frames are cleaned up on unmount.
- `ArticleCover` shares hover/focus zoom, color treatment, and an arrow across the homepage, article index/search, related articles, and research outputs. CSS owns these image transforms. Reduced motion retains the color/arrow cue without zoom or transitions.

## Known issues

- **Rare (~1%) reveal miss on the homepage specifically**, tied to its `ScrollSmoother` instance tearing down and recreating across navigation away from and back to `/` (recall: `shouldSmooth = pathname === "/"` in `smooth-scroll.tsx`, so `/` is the only route with a live `ScrollSmoother`). Gotcha #11's fix resolves this everywhere else (confirmed 0 repros across 300+ scripted navigations on every non-homepage route) but not reliably here — the `tl.scrollTrigger.progress` check can read a stale value while the smoother is mid-recreate. Not yet root-caused further; a real `ScrollTrigger.refresh()` call is _not_ the fix (see gotcha #11's note) — whoever picks this up should look at whether the check needs to wait for `ScrollSmoother.get()` to exist and have settled, not just at whether `smooth-scroll.tsx`'s own pathname-keyed effect has run.
- **PDF viewer toolbar / mobile keyboard focus**: fixed as of the mobile-responsive-audit work (see `docs/testing-verification.md`'s regression checklist) — noted here only so a future CSS `order-*` change on `publications/pdf-viewer-dialog.tsx`'s header doesn't reintroduce it. Visual (wrap) order and DOM (tab) order must stay in agreement; prefer reordering the DOM over `order-*` when the two would otherwise diverge.
